识屏，是怎么做到的

为什么苹果新 Siri 看一眼屏幕就能答，而「用时现抓」总是慢半拍 · 基于系统私有框架的符号分析

这篇在讲什么

很多人做屏幕 agent 的第一直觉是：提问那一刻，截个图喂多模态模型，或者抓一整棵 UI 树丢给 LLM。能跑，但慢——慢不在「用截图还是用 UI 树」，而在「用时才现抓、现处理一整屏」。

苹果其实两种来源都用（截图、UI 层级都在它的清单里，后面会看到）。区别不在用哪种，而在时机：它不在你提问时才去抓——屏幕内容平时就被结构化、写进了一个常驻库，识屏只是一次查询。

同样一个问题：「打给屏幕上这个人」。你的 agent 要花几百毫秒，苹果几乎瞬间。差在哪？

差别不在模型快慢，在架构。先把两条路摆在一起看。

✕ 用时现抓
  • 提问那一刻才抓：截图或抓 UI 树都一样，是冷启动
  • 给的是原始素材（像素 / 整棵树），模型得现场认
  • 整屏全喂，token 多、延迟高
  • 电话号是现场认出的字符串，还要再判断"这是不是号码、能拿它干嘛"
✓ 平时预建（苹果）
  • 平时就建好：内容提前被结构化、写进常驻库
  • 拿到的是结构化实体，进来就带类型
  • 按问题检索排序，只给相关的几条
  • 电话号是 OnScreenPhoneNumber + 现成的拨号 intent，直接能执行

关键认知：苹果把「识别」从「用时」挪到了「平时」。识别这步没有消失，而是被前置成了「写入」——所以提问时只剩查询。下面这个对比能直接看到时间差。

核心一

屏幕内容，平时就在写库

苹果有个常驻的「屏幕实体数据库」（私有框架 AppIntentsLiveEntitySupport，落地是一个 SQLite 库）。它通过三个 XPC distributed actor 读写——这是从符号里直接还原出来的：

Writer · update(feed:content:)
App 在渲染界面的同时，把「当前屏幕上有哪些实体」增量写入。支持 appending / removing，所以是实时维护，不是一次性快照。
Reader · state()
Siri 侧读库，一次拿到所有 LiveAppEntityFeed。不碰屏幕、不做识别。
Admin · databasePath()
管 schema、按 App 清理。确认它是真·落盘数据库，不是临时内存对象。

写进去的是 AttributedEntityIdentifier——只存 ID + 属性引用，不存大对象，所以写入极轻、可以高频更新。这就是「识别被前置成写入」的物理形态：

核心二

所有屏幕，归约成一套语义元素

不是每个 App 都会主动写库。没写的怎么办？苹果还有一套统一的语义元素模型 IntelligenceElement（框架 UIIntelligenceSupport）：不管原生控件还是网页，最后都被归约成同一套带类型的树。从符号里数出来的类型：

  • 文本类　Text · Document · ImageMedia
  • 控件类　Button（带 Role：primary / cancel / destructive）· Toggle
  • 结构类　Table / TableRow / TableCell · Collection / CollectionItem / Section · NavigationSplitPane
  • 容器类　Window · Screen · Scrollable（带 ScrollPosition）

关键机制：每个组件自己实现 intelligenceSubelements()——控件主动吐出自己的语义子元素，由收集器沿层级拼成树。这是「组件自报家门」，不是系统去截图猜。

网页这种「一大块」怎么办？

网页对系统是 WebKit 渲染的一整块，不像原生控件天然带类型。苹果给了专门通道 wka（WebKit Awareness）——符号里有 WKAccessibilityWebPageObject 和开关 wkaPassages / wkaHandoff：

  • wkaPassages：WebKit 把网页正文经 accessibility 通道切成段落（passages），导出成 OnScreenUIText，而不是给一张图。
  • 再在文本上叠带字符区间的实体：DetectedLink(url, textRange)、DetectedPhoneNumber(.., textRange)、DetectedAddress(.., textRange)——「原文第 x–y 个字符是个电话」。

所以网页上的电话能直接点拨：它不是从截图 OCR 的字符串，而是一个挂着拨号动作的强类型实体。

核心三

一条降级阶梯：结构优先，像素兜底

把上面拼起来，就是识屏的完整优先级。符号里的 OnScreenContentSources 是个 OptionSet，正好对应这四级——从快到慢，能在上面解决就绝不往下走：

1
appEntities · 读实体库
App 已主动写入。一次查库就拿到结构化、带类型、带 intent 的实体。
最快
↓ 库里没有，退一步
2
uiHierarchyContent · 读语义树 / wka 段落
控件 / WebKit 通过 a11y 自报的 IntelligenceElement 树。已存在的结构，直接读。
低
↓ 结构拿不到，再退一步
3
windowContentGeneratedPDF · 窗口转 PDF
把整窗渲染成带分页的 PDF（_intelligenceWritePDF），文本可选、保留版面。
中
↓ 全都没有，最后兜底
4
appWindowSnapshots · 截图
最后才走 _intelligenceCaptureCGImage 截屏，交给视觉识别。
最慢

你的 agent 默认从第 4 级（截图）起步——等于每次都在重做苹果提前做好的事。苹果绝大多数情况停在第 1–2 级。

核心四

完整链路：从一屏，到一个能点的实体

把前面三节串起来，看一条内容从屏幕到「可执行实体」实际走的五步——每步都有对应的真实符号：

1
遍历采集 FragmentCollector
沿 UI 层级遍历（traverseHierarchy，带祖先和窗口），不是截屏。关键：只收看得见的（fractionVisible 过滤被遮挡 / 划出屏的），还能「只要布局不要内容」（collectWindowLayoutOnly）省开销。
↓ 一边遍历，一边顺手做一件事
2
顺带抓「能做什么」 appIntentsRequest
采集每个元素时，同时把它能触发的 App Intent 一起抓出来。这就是「看到即可执行」的来源——电话号在被收集的那一刻，就已经挂上了「拨号」这个动作。
↓ 整理成结构
3
归约 + 抽实体 IntelligenceElement
收上来的碎片拼成统一语义树；在文本上叠带字符区间的强类型实体（DetectedPhoneNumber(.., textRange) 等）。到这内容已经「带类型、带位置、带动作」。
↓ 存好，等人来问
4
缓存 + 预热 prewarm / refresh
结果落进 UIContext 缓存，后台 prewarm / warmup 提前备好、refresh 增量更新。用户提问前，这一切就绪了。
↓ 提问那一刻，只剩这步
5
检索排序 retrieveAndRankContextValues(query:)
按你的问题对缓存里的实体排序、按 threshold 截断，只取最相关的几条给模型。命中的实体自带 DetectedAppIntent，可直接执行。

看清这五步就明白它为什么快：第 1–4 步全在你提问之前、后台就做完了；提问时只剩第 5 步「排个序」。截图 + 模型的做法，相当于每次提问都从第 1 步重头跑一遍，还得用视觉模型现认。

核心五

跨应用：屏上看到一首歌，怎么跳到别的 App 播

你在某个 App 里看到一首歌，说「播放这首歌」——它能拉起音乐 App 放出来。识屏只「看懂屏幕上是一首歌」，跨到另一个 App 去执行，靠的是什么？

靠的是两套已经讲过的机制对接，而不是某个专门的「跨应用」黑科技。两个有据的事实：

1
识屏给的是「带类型的实体」，不是图
前面讲过：屏上那块被识成带语义类型（SemanticContentType）的实体——「这是一首歌曲」，而且采集时就挂上了可执行的 DetectedAppIntent。
↓ 类型对上 App 声明的类型
2
App 通过 App Intents 声明「我能处理歌曲」
音乐 App 实现了标准的「播放媒体」意图（INPlayMediaIntent），声明自己吃「媒体 / 歌曲」这种类型。类型对上，这首歌就能交给它执行。

所以「跨应用」的本质不是「Siri 钻进了 Apple Music」，而是类型把两边接上了：识屏产出带类型的实体，App 声明能处理这个类型，系统把实体当参数交给那个 App 的标准 intent 执行。歌曲如此，「在地图打开这个地址」「用某 App 买这件商品」是同一个道理——都靠「语义类型」这个共同语言。

坦白一处：「识屏实体 → 选定哪个 App → 强转成参数」这中间的精确调度步骤，符号层没能完整串起来——上面只列了两端确凿的事实（实体带类型 + App 声明类型 + 标准媒体 intent 存在），中间的选 App / 参数绑定是合理推断，不当成确证。能确定的是：这条桥靠「语义类型」对接，和前面所有「封闭标准」一脉相承。

核心六

那「举起相机问现实」呢？那是另一条路

前面讲的是系统自动识屏——平时建好、用时查库。但还有另一件事容易和它混：用户主动举着屏幕问「这是什么花？」「这个商品哪买？」。苹果把这条单独叫 Visual Intelligence（视觉智能），走的是另一条路。

自动识屏
  • 系统自动、平时就建好
  • 走结构化实体 + 缓存
  • 符号：OnScreenContent
视觉智能 · 问现实世界
  • 用户主动举起相机问才触发
  • 对象是现实里的东西（拍下来）
  • 符号：CameraCapture · VisualIntelligence

注意这里的对象——不是屏幕，是现实世界。Visual Intelligence 主要是你举起手机对着实物问：「这是什么花？」「这家店几点关？」「这件衣服哪买？」（符号里有 CameraCapture 一整套 + BusinessLookupProvider 查店铺）。它的输入是相机画面，所以必然要拍下来过视觉——和「自动识屏」走结构化是两条完全不同的路。

但苹果在「拍了再问」这条路上多缝了两层

它不是把照片一股脑丢给大模型，而是：

拍下画面
CameraCapture
→
端侧视觉先过
OCR / 物体 / 商品 / 店铺
能答就地答
→
图 + 已识别文字
imageAndText 一起喂模型
  • 上模型前，端侧视觉先啃一遍。textRecognition(OCR) / objectness(物体) / productLookup(商品) / BusinessLookup(店铺)——端侧能直接答的（认字、查商品、查营业时间），就地解决、不上大模型。这一层就是「本地视觉，快又通用」。
  • 真要上模型，也是「图 + 文」一起喂。符号 imageAndTextInput：不只给像素，把端侧已识别出的文字 / 实体一并附上——等于先帮大模型把画面读了一遍，省了「先认再理解」。

所以「视觉智能」走的是拍照 + 视觉，和自动识屏不是一回事——一个问现实（相机）、一个懂屏幕（结构化）。但它在视觉这条路上的功夫，和你的 agent 思路同源：端侧先过滤、能就地答就不上模型、上模型也连文字一起喂。

核心七

那图片里的内容呢？比如「一个金发女生」

屏幕上是一张照片：一个金发女生。我问「屏幕上是什么」——这里没有控件、没有 UI tree、没有文字，全是像素。前面那套结构化机制根本够不着。它怎么办？

这正是结构化的边界。到了纯图像内容，确实回退到视觉——但苹果没有粗暴地「截全屏丢大模型」，而是把图片当成一个独立的内容项来处理。符号里这张图是 OnScreenContent.Image，带三个字段：image（像素本身）、isSnapshot（是不是截的）、entity（关联的实体）。处理还是分档：

1
端侧先「读图」，把像素变成文字 imageCaptioner
端侧有个图片字幕模型（imageCaptionDecoder，按需下载），把图描述成一句话——「一位金发女性的肖像」。还叠 faceDetection(人脸) / OCR / 物体检测。产出 imageCaptionResult 进上下文。这一步是视觉，但仍是端侧、轻量、结构化（出的是文字）。
↓ 简单问题，到这就够了
2
能就地答的，不上大模型
「这是人像吗 / 有几个人 / 上面写了什么字」——端侧 caption + 人脸 + OCR 的结果直接答，省了大模型。
↓ 真要深问，才升级
3
复杂问题：连图带描述一起喂多模态 imageAndTextInput
「她什么表情 / 这像谁的画风」——把那一张图（不是整屏）编码成视觉 token（encodeImage / imagePromptComponent），连同问题、连同端侧已 caption 出来的文字，一起喂多模态模型。

所以回到你的问题：金发女生这种纯图像内容，确实绕不开视觉——但苹果的做法是「只取那一张图、端侧先 caption 成文字、能就地答就不上模型」。它把视觉这条路也做成了「先端侧结构化、再按需升级」，和前面文本那套是同一个哲学，只是把「OCR / 解析」换成了「caption / 人脸检测」。

一句话收口：结构化够得着的（控件、文字、实体），平时就读好缓存；够不着的（图片像素），端侧视觉先 caption 成文字，最后才连图喂模型。从控件到像素，是一条连续的「能结构化就结构化、不能才上视觉、上视觉也先端侧」的降级链。

落地

你的 agent 怎么改

不需要 App Intents，这套思路任何平台都能搬。按性价比排序：

  1. 建一份常驻「屏幕缓存」，别每次重抓。维护一份结构化屏幕状态，UI 变化时增量 append / remove，而不是每次全量截图。query 来时读缓存。
  2. 优先读结构，截图当兜底。能拿 DOM（网页）/ a11y 树（原生）就别截图。归约成统一语义元素（text / button / table / link…）。
  3. 预抽实体并挂动作。抓到文本立刻用规则 / 小模型抽出 链接 / 电话 / 地址 + 字符区间，并绑定可执行动作。别留给大模型现抽。
  4. 检索而非全喂。query 来时对缓存做检索 + 排序 + 可见性过滤 + 超时，只把 top-k 相关片段给模型。
  5. 降级链。结构命中就用；拿不到再 PDF / 截图。把视觉识别压到最后，而不是当默认入口。
  6. 问屏：截图前先过端侧视觉，喂模型时带上文字。用户主动问屏躲不开截图——但学苹果，先用本地 OCR / 检测啃一遍，能就地答的别上模型；真要上，把 OCR 出来的文字连图一起喂（imageAndText），别让大模型从零看图。

苹果不是「识屏快」，是把识别从「用时」搬到了「平时」。

你要快，就别在提问时才去看屏幕——平时就维护好一份结构化、可检索、带动作的屏幕缓存。
