从一句话到一张卡片

苹果 iOS 27 新 Siri 的生成式 UI 是怎么工作的 · 基于 AgentCanvasUICore 框架

开始之前，先说清「生成式 UI」

先说生成式 UI是啥：你问一句，AI 不只回你一段文字，而是当场把答案拼成一张界面——该上卡片上卡片、该配图配图。它分两半：一半是大模型决定「说什么、用哪些块」，另一半是系统把这些块画成好看的界面。

本文讲的 AgentCanvasUICore，就是后面那一半——iOS 27 新 Siri 用来把答案画成卡片的那套系统机制。下文说的「块、识别、渲染、降级、动画」，全是它的活儿。所以标题说「生成式 UI 怎么工作」，讲的主要就是界面是怎么长出来的这半边。

想象你问 Siri：「珠峰有多高？帮我配几张图。」

大模型那一端，吐出来的并不是你最终看到的卡片，而是一串带标记的纯文本。它大概长这样：

# 珠穆朗玛峰

世界最高峰，海拔 <callout value=8849 unit="meter">8,849 米</callout>。

<imageCollection style="montage">
  <image url="..." width=2240 height=1260/>
</imageCollection>

模型的活到此为止。你看上面这段——它吐出来的就是这些：一个 # 标题、一段文字、一个 <callout> 数值、一组 <image>。它只决定「说什么、用哪种标记」；至于这些标记最后渲成多大字号、什么间距、怎么浮现上屏——代码里一个像素都没提，那是后台的事。这就是它和「直接画 UI」最根本的区别：模型产出的是「内容 ＋ 类型标记」，不是外观。

还有一点同样关键：它能用的标记就那么固定的一套（#、<callout>、<image>……约二十种），多一种都没有。它没法临时发明一个 <weather> 或 <chart> 让系统去画——想表达这些，只能用现有这二十来种里的几样拼出来。正因为产出被收窄到「有限的内容 ＋ 有限的标记」，后台才能把它稳定地变成屏幕上那张优雅卡片——而这，正是接下来几幕的事。

第一幕

认出它是什么

同样一段文字进来，系统要做的第一件事，是把它拆成一个个「块」（block）。所谓「块」，就是一段能独立成形的内容单元——一个标题是一块、一段正文是一块、一张表格是一块、一组图也是一块。整张卡片，就是这些块自上而下码起来的。把长文本切成块，是后面一切的起点。

而在切块之前，还有个聪明的设计：苹果让内容支持两种写法，代码里叫 Markdown.Flavor（直译是「风味/变体」）。

swiftMarkdown
标准 markdown。标题、列表、表格、代码、引用、数学公式——凡是通用 markdown 能写的，都走这条。
pseudoMarkdown
苹果自定义的标签写法。图集、callout、折叠面板、自定义卡——markdown 表达不了的富媒体，才用 <tag> 包裹。

要先澄清一个误解：系统并不会去「猜」一段文本该用哪种写法。框架里找不到任何检测、推断的代码——Markdown 的构造器里，flavor 是一个直接传进来的参数。也就是说，用哪种写法是调用方（喂内容进来的那一端）说了算，在创建内容的那一刻就定死了，不是系统拿到文本现去判断的。

这里要拦一个顺理成章的疑问：「既然不猜，那它怎么知道 # 是标题、<image> 是图片？」——注意，「不猜」和「认得出」是两件事。上面说的「不猜」，只针对选哪种写法这一步（那是传参定的）。至于 #、<image> 这些具体标记，系统当然要认——但认它们靠的是规则，不是猜。差别在于：「猜」是拿一段没有标记的文本去推断它像什么；而这里，模型早就把标记明明白白写上了——# 是它打的、<image> 是它包的。系统要做的，只是照着这些明文标记去对规则，就像程序认 if 关键字一样确定，没有歧义、不会蒙错。

所以真正的问题不是「猜不猜」，而是：这些明文标记，系统具体怎么对规则认出来？一段文本里，怎么知道这一截是标题、那一截是表格、这里是公式、那里是图片？两类标记，用的是两套完全不同的识别机制。

标准那条路：交给现成的解析器

swiftMarkdown 这条路，AgentCanvasUICore 自己根本不做识别。它把文本转手交给一个独立框架——CampoMarkdown.framework（Campo 是 iOS 27 Siri 的内部代号）。这是个成熟的标准 markdown 解析器，它天然就认识 markdown 的所有通用约定：

  • # 开头 → 这是标题
  • |…|…| 加分隔行 → 这是表格
  • 三个反引号 → 这是代码块
  • $…$ 或 $$…$$ → 这是数学公式

识别完，每一截文本就被贴上了类型标签。这一层的识别，AgentCanvasUICore 没有自己重写，而是直接复用了这个成熟的解析器。

举两个例子。表格：模型吐出 | 列1 | 列2 | 再跟一行 |---|---|，CampoMarkdown 按 markdown 的通用规则一看就懂——这是表格，于是切出一段「表格」。标题、公式、代码块同理，都是这个解析器按既有规则认出来的，AgentCanvasUICore 全程没参与。

自定义那条路：扫标签、查名字

但图片就不一样了。markdown 虽然有图片语法，可苹果要的是带宽高、能拼图集、能进沉浸态的富图片，标准 markdown 表达不了——于是它发明了自己的标签 <image url="..." width=2240/>。这类标签（<image>、<callout>、<accordion> 等）就得苹果自己识别了。核心是一个叫 MarkdownStreamer 的引擎，识别逻辑很朴素：

  1. 流式扫描。模型边吐字，它边 consume，一边读一边找尖括号 < >。
  2. 等标签闭合。commitIfXMLBalanced——确认像 <callout>…</callout> 这样首尾配对、XML 平衡了，才提交，避免把吐到一半的半截标签当真。
  3. 拿名字查表。扫到 callout 这个名字，就用它去 TagName(rawValue: "callout") 查那张约二十个标签的封闭清单。

说白了就是拿名字去对清单：扫到 callout，就拿这个名字去那张写死的标签清单上比对，看在不在册。在，就按它对应的渲染方式走；不在，就当成一个「不认识的标签」，先记下来，留给第五幕的兜底机制处理。这张清单统共就约二十项，模型写不出清单之外的第 N+1 种——硬写，也会在这一步被认成「未知」。

到这里，原本一长串文字，就被切成了一段段、贴好了标签：这段是标题、这段是图片、这段是 callout……像一份理好的清单，一条一条，每条都标明了「这是什么、它带了哪些参数」。

识别，到此结束。系统已经知道每一段是什么了。接下来的问题只剩一个——怎么把它们画出来。

第二幕

交给对的人去画

拿到这份贴好标签的清单，系统就一段段过：看它是什么类型，就派给专门画这种内容的那个「画师」。负责分派的角色叫路由器——它不画，只管把每段送到对的画师手上；而每一种内容，都有一个只画它这一种的画师，官方名字叫渲染器。标题有标题的渲染器，表格有表格的，图片有图片的。

关键是：这些渲染器长什么样，是设计师早就定死的——字多大、行距多宽、圆角多圆、标题用什么字阶，全都提前写好、固定不变。模型决定不了任何一个像素：它只能说「这是个标题」，至于这个标题最后被画成什么样，完全由渲染器说了算。模型能伸手的，顶多是「主题色」「相对大小」这么几个事先留好的旋钮（下一幕再说）。这些渲染器的名字都以 richText 开头：

  • 文本类　richTextHeader · richTextParagraph · richTextTextBlock · richTextList · richTextBlockQuote · richTextPullQuote · richTextDivider
  • 结构类　richTextTable · richTextTableHeader · richTextTableCell · richTextCode · richTextAccordion · richTextTaggedBlock
  • 媒体类　richTextImage · richTextCallout（Collection）
  • 其它　richTextSourceAttribution（出处）· richTextCustomView（自定义卡）· richTextPlaceholder（占位）

注意一个细节：表格、代码、标题这些有渲染器，却没有自己的标签。因为它们的「识别」发生在第一幕的标准 markdown 层，到这里只管「怎么画」。整套系统的权力划分，可以用三个数字概括：

不过「写死」要小心理解——定死的是「规则和档位」，不是「具体像素」。翻代码会发现，渲染器里几乎找不到绝对像素值：字号是 CanvasTextSize.relative（相对值，用户只能 increase / decrease / reset 调档，调不出任意大小）；高度是 displayRelativeHeight（相对高度）＋ 内容驱动，再配一套裁切状态机（ClipState：完整可见 / 尾部截断 / 完全截断）判断要不要收起；容器还分 compact / regular 两个响应式断点。

所以同一张卡，在大屏小屏、长内容短内容下会自适应地伸缩，但永远落在设计师圈定的范围内。这比「把每个像素填死」更高级：设计师定的不是一张张静态稿，而是一套会自己算尺寸的规则。模型那点开放权限（主题色、相对档位）也都卡在这套规则内——动得了观感，动不了骨架。

至于「业务要塞自己的原生卡片」怎么办——天气、股票、地图，这些规范里没有的东西？答案藏在后面的兜底机制里，<view> 自定义卡其实是那条降级链上的一环。先按下不表。

第四幕

让它优雅地出现

块画好了，但不能「啪」一下全蹦出来。怎么逐字浮现、怎么排队进场——这是动画规范，也是最讲究、最容易让人犯迷糊的一层。

先解开一个常见的结：动画其实是两件不同的事，很多人会缠在一起——

A · 特效
单个元素自己怎么动。文字逐字浮现、图片揭示、卡片整块弹入——每种块都不一样。
B · 组合
多个元素之间怎么排在一起。靠 cascadeThreshold 错峰，一块接一块。

记住这个分法，下面就清楚了。先看 A · 每种块各自的特效——注意它们真的不一样，不只是文字。

文字 · 逐字浮现

段落文字按逐字 / 逐词浮现（StreamingTextEffectStyle，三档）。关键细节：每个字带一点模糊（blurFade），spectral 还有色差折射——这是它"柔"的来源，不是生硬淡入。

Elasticity · 重排时的弹性让位

这是另一种动画，和"进场"不是一回事。前面讲的都是"块第一次出现"；Elasticity 管的是块已经在了、但因为邻居变高要挪位的情况——最典型的就是图片异步加载：文字先到位，图片还在加载，等图片加载完撑开高度，下面的内容就得往下让。

A 讲完了——三种块，三种完全不同的进场。那 B · 组合 呢？这才是"图片+文字、卡片+文字到底怎么配"的答案。

没有「组合专属配方」

很多人以为"文字+图片"有一套配方、"文字+卡片"有另一套，要分别设计。但苹果根本没有任何组合专属配方——二进制里搜不到 textImage / textCard / combo 这类东西。

只有一条通用规则，所有组合都走它：每块用自己的特效进场，块之间用 cascadeThreshold 统一排队。

所以无论怎么组合——配法完全一样：块按顺序排好，第一块用自己的特效进场，进到阈值后下一块开始，往下"码"。下面这条回答就是文字 → 卡片 → 卡片，三块各用各的特效、之间用同一个 cascade 衔接：

那第二个块，怎么知道该出场了？

答案就藏在前面那个 cascadeThreshold 里。第一个块不是"完全出现完"才轮到第二个——那样会一顿一顿的。它的真正机制是：

进度，不是完成
系统盯着第一个块的进场进度（spring 走到百分之多少）。比如阈值设 45%——第一块进到 45%，第二块就开始，不等它走完。
所以是叠着出
第二块开始时，第一块还在动。两块有一段重叠，看起来就是流畅地"一个推一个"往下码，而不是僵硬地排队。
阈值决定节奏
阈值低（如 20%）→ 块几乎同时涌出，快而满；阈值高（如 90%）→ 一个走得差不多了下一个才来，慢而稳。

说白了：cascade 不是"出现完了通知下一个"，而是"我进度到点了，下一个自己就开始"。每个块只关心自己进到哪了，到了阈值就放行下一个——一条简单的规则，串起任意多个块。上面 demo 的「Cascade 阈值」滑块调的就是这个百分比，你能直接看到节奏变化。

底层所有这些进场，都由同一套三组 spring 驱动——位移、透明度、特效各一条曲线（springOffset / springOpacity / springEffects）。所谓 standard、弹性，不过是同一组 spring 调成不同的回弹量。

一句话收口

A 特效（每块自己怎么动）和 B 组合（cascade 排队）是两件事。不用记 N 种配方，只用记一条规则 + 每种块的特效。

第五幕

它从不失败，只降级

现在回到那个一直按着没讲的问题：模型要表达一个东西，可系统不一定有对应的块——天气卡、股票卡，甚至一个谁都没见过的标签。系统怎么办？

它从不报错、从不留白。面对任何内容，它沿着一条降级阶梯从上往下试，总有一级能接住。这就是整套规范的安全网，一共四级：

第 1 级

有专门块 → 用专门块

能对上 image、table、callout 的，对号入座，最佳呈现。这是最理想的一级。

第 3 级

需要原生卡 → 自定义视图

业务想塞自己的卡片（天气 / 股票 / 地图 / 打车），用 <view id="..."/>。宿主 App 通过 CustomViewsSource 注册好视图，模型吐出对应 id，系统就把那张原生卡渲染进内容流里。第二幕按下没讲的「卡片」，就落在这一级——它不是旁支，是降级阶梯的一环。

第 4 级

完全不认识 → 兜底处理器

遇到压根没见过的标签，UnrecognizedTagHandler 接管：忽略那个标签，但保留里面的文字。绝不崩、绝不空。

介绍下金门大桥
模型吐出：金门大桥的官方色叫 <hologram fx="3d">International Orange</hologram>。
系统不认识 <hologram> → 丢掉标签，保留文字 ↓
金门大桥的官方色叫 International Orange。
最笨的一层，但保证无论模型吐出什么，都不会崩、不会白屏。最后的安全网。

四级连起来看，会发现一个优雅的递降：专属呈现 → 纯文字 → 自定义卡 → 保底文字。越往下越朴素，但永远有底。

这背后是一句设计哲学：格子就那么几种，但后厨永远兜得住。复杂度不靠「做一张能表达一切的超级卡片」，而靠「用有限的几种格子，流式地拼出无穷的组合」来消化。模型能填的被锁死在安全范围内，体验的下限被牢牢托住——所以无论模型填出什么，最后总能从一句话，变成一张卡片。

大模型负责「说什么」，这套规范负责「怎么呈现」。
