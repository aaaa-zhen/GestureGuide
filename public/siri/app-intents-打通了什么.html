Siri 背后的一整套机器

模型怎么分端云、第一方应用开放了什么、第三方怎么接、十万条数据怎么不崩 · 基于系统私有框架的符号分析

这篇怎么读

「苹果 AI」不是一个模型，是一条流水线：你说一句话，先决定用端侧还是云端的模型去想，想出「要做什么」后，去调本地应用开放的标准动作，第三方设备和 App 也从同一个口子接进来；而当某个应用的数据量很大（比如一万张照片），还得有专门的办法保证不卡死；要是你一口气说了好几件事，它还得拆开排好序。

本文顺着这条链，一节一节拆开看它到底怎么搭的。

第一节

模型：什么走本地，什么上云

苹果的模型是端 + 云两套，会自动路由（符号里能看到成对的 AnswerSynthesisServer 和 AnswerSynthesis…PrivateCloudCompute，按 deviceCapability 判定走哪条）。两套各管一摊：

🟢 端侧小模型
on-device · 默认
  • 日常意图理解、改写、校对
  • 短问答、通知摘要
  • 对屏幕 / 数据的快速操作
  • 最快、最私密，离线也能用
🔵 Private Cloud Compute
苹果保密云 · 升级时
  • 复杂推理、长文总结
  • 更准的图片分析、长上下文
  • 端侧 UnsupportedOnDevice 的请求
  • 跑在苹果自营、可验证隐私的云上

怎么决定走哪条——不是模型临场拍脑袋，是按设备能力 + 任务复杂度预先判定（deviceCapabilityFlags / HWCapableSiriON / flag pccAsDefault）：

1请求进来，先看设备够不够、任务复不复杂。
2简单 / 隐私敏感 / 设备够强 → 就地用端侧模型。
3端侧扛不住（报 UnsupportedOnDevice）→ 升级到 Private Cloud Compute。

但有个最容易搞混的点

上云，只让它「想」得更聪明，不让它「做」得更多。云端模型更大，所以分析更准、总结更好——但它能执行的动作，还是后面要讲的那张固定清单。云端不会凭空多出一个新能力。「智能」靠上云提升，「能做什么」是另一层决定的。

那云能直接改本地的应用吗？——不能

这是关键的隐私边界。从符号看，云端产出的是一份「执行计划」（executionPlan），不是动手本身。真正去调用 App、改数据的，是端侧的执行器 ExecutorAppIntent——它在本地跑，所以才会报「蓝牙没开」「定位没开」「实体没找到」这种只有本地设备才知道的错误。

云端模型
想出「该做什么」
executionPlan
→
计划回到端侧
不带着你的数据上云执行
→
端侧执行器
ExecutorAppIntent
本地真正动手

所以：云负责「想」，端负责「做」。动作永远落在你设备本地执行，云端拿到的只是问题，不是你应用的控制权。

补充

它的答案到底从哪来——是谷歌吗？

你问 Siri 一个问题，它的答案是去谷歌搜的吗？

不一定——「搜」其实分三条路，看你问的是哪种：

① 开网页去搜
「搜一下 XX」这种要打开网页结果的——用你 Safari 里设的默认引擎（多数人是 Google，也可改 Bing / DuckDuckGo / 百度…）。苹果不锁死，跟你的设置走。
② Siri 直接答的知识
「珠峰多高」「换算单位」这种不开浏览器、直接给答案的——走苹果自己的知识库（AppleKnowledgeBase）+ 它自有的搜索 / 答案合成引擎 OmniSearch（OmniSearchAnswerSynthesis）。不是谷歌。
③ 复杂开放问题
端侧 / 苹果云答不了的开放问题——询问你同意后转给 ChatGPT（符号里连账户体系都有）。单独一条、要授权。

所以「搜谷歌还是」的准确回答是：开网页搜 = 你设的引擎（默认多是谷歌）；但 Siri 的智能问答不靠谷歌，靠它自己那套（OmniSearch + 苹果知识库），搞不定才上 ChatGPT。这也呼应上一节——「智能」可以借外部（引擎、ChatGPT），但答完要「做」的动作，仍走端侧那张固定清单。

第二节

第一方应用，开放了什么

模型想好「要做什么」之后，靠 App Intents 去调应用——每个动作都得是应用按苹果预设的标准「动作域」主动暴露的。下面是从系统里实际扒出来的、各应用打通的程度：

📷 照片 深
建/删/改相册、加移照片、搜索、编辑（带连续数值）：裁剪/拉直/曝光/饱和/暖色/景深/滤镜、清理路人、收藏回忆、识别人物。photos.createAlbum · updateAsset · deleteAssets
📝 备忘录 深
新建/删除/搜索/查找、加附件、改手写内容；外加总结、改写。notes.createNote · delete · find · updateHandWriting
✅ 提醒事项 深
建/改/删提醒、建清单/分区/标签、加任务、搜索——颗粒度很细。reminders.createReminder · createList · createTag · addTask · updateReminder
🏠 家庭 深
开关配件、运行场景、自动化；亮度/色温/温度等连续特征。SetAccessory · ToggleAccessory
✉️ 邮件 中
发送、回复（归档/删除）、搜索、按发件人。mail.sendMail · reply · search
💬 信息 中
发送/回复/搜索、发给联系人。messages.send · reply · sendingMessageToContact
📅 日历 中
建/改/删事件、显示。calendar.createEvent · updateEvent · deleteEvents
📞 电话 中
打电话、发起会议通话、紧急呼叫。phone.startPhoneCall · createConferenceCall · startEmergencyCall
🎵 音乐 / 播客 / TV 中
播放、队列、播放列表、搜索、章节。music.playback · playlist · search · podcasts.playback · tv.search
🧭 地图 中
开始导航、横幅显示。maps.startNavigation · showBanners
🌐 浏览器 中
开/关标签、书签、搜网页、用户上下文。browser.createUserContext · bookmark
🏃 健身 / 📁 文件 / 📷 相机 基础
开始锻炼、文件书签、相机开启等单点动作。fitness.startWorkout · files.bookmarks

这套覆盖远比一般人想的广，而且颗粒度不浅——提醒事项连「建标签 / 建分区」都有独立动作，照片连修图滑块都暴露成带数值的动作。

但「办公文档」这类要泼盆冷水。常以为 word / 表格 / 演示文稿也有一套标准动作域——可在符号里找不到它们干净的动作 schema（搜到的 document.* 其实是网页 DOM 接口，不是 Siri 动作）。真正确凿的文档类动作只有 Freeform（FreeformCreateBoardIntent 建白板）。所以「文档全打通了」更像想当然——有标准域的才打通，没有的就是没有，这正好印证「应用只能往苹果预设的域里填、填不出域外的动作」。

同样叫「打通」，深浅差很多

从浅到深四级，决定一个应用能被 AI 用到什么程度：

1
能打开
把应用拉起来、跳到某页。最浅，几乎都有。
2
能读 · 能搜
内容是结构化实体（NoteEntity/AssetEntity），能检索、能引用「这条」。
3
能改 · 能执行动作
建相册、发邮件、开灯——离散操作。多数「中」级到这。
4
能调连续参数
最深。曝光/饱和、亮度/色温——滑块级数值控制（符号里就是 adjustment value）。照片、家庭到了这。

照片能到第 4 级，是因为苹果把每一个修图维度都单独做成了带数值的 intent。不是「AI 看懂了照片」，是「应用把调色板每个旋钮都接了出来」。

第三节

第三方，怎么接进来

上面都是苹果自己的应用。第三方设备和 App 能被 Siri 掌管吗？能——但方式很说明问题：不是 Siri 去对接你，是你来对接苹果的标准。

第三方
硬件 / App / 你的流程
→
三选一接入
HomeKit / App Intents
/ App Shortcuts
→
Siri 能调
Entity / 标准动作
/ 自定义短语

不只智能家居——第三方接入其实有三条路，从「最贴标准」到「最自由」：

① 智能硬件 → 走 Matter / HomeKit

第三方设备（灯、锁、传感器）接入 Matter / HomeKit，就成了一个 AccessoryEntity。Siri 不区分一方三方，统一按 home.* 标准动作调（开关、亮度、色温、场景）。但只能做 HomeKit 抽象出来的特征——灯就是「开关 + 亮度 + 色温」，别的花样够不着。

② 第三方 App → 实现 App Intents，对上标准动作域

普通 App（不是硬件）实现 App Intents，把自己的能力声明成 AppEntity + 动作。但前提是「对上苹果预设的 AssistantSchema 域」——你是个记账 App，能对上「创建一条记录」这种标准动作就能被 Siri 直接调；对不上标准域的独门功能，Siri 调不到。这条最贴标准、也最受限。

③ App Shortcuts / 快捷指令 → 自定义短语 + 模型帮你生成

这条最自由，也是你说的「场景助手」那条线。基础是 App Shortcuts：App 给自己的动作配自定义触发短语（AppShortcutPhrase）——「嘿 Siri，开始我的冥想」直接触发某个冥想 App，不用对上任何苹果预设域。在它之上，快捷指令（Shortcuts）能把多个 App 的动作串成工作流（WFAction 链）+ 自动化触发（AutomationTrigger：到家 / 某时间 / 碰 NFC / 进专注模式）。

关键变化：现在是「模型帮你 vibe 出快捷指令」

过去快捷指令的痛点是得自己手动拼积木，门槛高。Apple Intelligence 把这条彻底改了——符号里能看到 ComposeWorkflow / WorkflowGeneration：

  • 自然语言生成整条工作流。你描述「想要什么」，模型生成对应的快捷指令（generateShortcutRepresentation / WorkflowGenerationItem）——不再是你一块块拖。
  • 工作流里能直接塞一步「调模型」。UseModelAction / IntelligenceAction：在一条快捷指令中间插入「让模型处理这段」——比如「读取邮件 → 让模型总结 → 发给我」。模型成了工作流里的一个可调动作。

所以这条路不再「脚本化、费手」：你用一句话描述意图，模型 vibe 出快捷指令；流程里还能随时让模型帮忙。它把「自由度」和「省心」第一次拉到了一起。

三条路连起来看，是一道逐渐放开的光谱：① ② 走标准域，被 Siri 智能调度、最省心，但只能做标准里有的；③ 快捷指令最自由、能自定义短语 + 跨 App 串联，而且现在能让模型替你生成、还能在流程里调模型——自由和省心不再二选一。这是苹果在「封闭标准」之外，给第三方留的、而且正在变聪明的那条路。

第四节

数据量大了，怎么不崩

手机里有一万张照片，你说「找出很多年前在海边那张」——它真能找到。怎么做到的？

注意：「找到那张」和「裁剪/存相册」是两件事。后者是上面的 App Intents（执行）；前者是检索，是另一套专门对付规模的机器。它的核心思路是——不在你提问时翻一万张，而是平时就把每张照片转成一个数值向量、建好索引。

1
平时：后台逐张「向量化」
守护进程 photoanalysisd 在充电/空闲时把全库跑一遍，用 CLIP 给每张图生成语义向量（CLIPBasedAssetSummarizer），落盘成索引（embeddingStoreDirectoryForPhotoLibrary）。照片越旧，越早被索引好。
2
用时：查索引，不查照片
你的描述也转成向量，在索引里做数学最近邻匹配（cosineSimilarity）。和照片新旧、库多大无关——查的是现成索引，不是现场翻图。

这也顺带绕开了「大模型幻觉」：大模型不参与「找」。它最多把你的话转成向量，挑哪张是确定性的向量计算——同样输入永远同样输出，不会「这次找得到、下次找不到」。存的是稳定的数值向量，不是大模型每次都可能写不一样的文字标注。

那一万张、十万张，怎么扛住？

规模问题就两块——存得下、搜得快。苹果用的是工业级向量检索的标准三招，符号里都有对应件：

存得下
量化压缩：不存每张图完整向量，用「码本里的质心」近似表示（CLIPCentroidCodebook / CLIPClusterer）。十万张也压得很小。
搜得快
聚类剪枝：先选相关的几个簇，只在簇内找，不全扫（CLIPElector / CLIPElectorCluster）——这就是近似最近邻，库再大也接近常数时间。
不卡死
后台分阶段 + 让路：充电/空闲才跑，前台一来就退，扛不住就降级丢弃（analysisStage / backgroundProcessingIsAllowed / lowPower）。

核心思想一句话：用「近似」换「规模」。它不追求在十万张里找到数学上绝对最近的那张，而是先分桶、只在最相关的桶里找近似最优——牺牲一点点精度，换来「库再大，搜索也几乎一样快」。这就是为什么你十万张照片，搜起来和一千张感觉没差别。

第五节

一句话里好几件事，怎么排

「看下天气、查我下午的航班、把刚拍那张照片调亮存进相册」——一口气三件事，它怎么办？

这种叫复合请求（符号里就是 compoundRequest）。系统不会把整句囫囵丢给模型硬答，而是先拆成一个个步骤（planStep / ExecutionStep），每步对应一次工具调用，再排出执行顺序。排序的依据，是步骤之间有没有数据依赖（dependencyGraph）：

1
拆解
一句话 → 三个步骤：查天气 / 查航班 / 调图存相册。每步绑定一个 App Intent + 参数。
2
看依赖，定并行还是串行
三件事互不依赖 → 并行同时发（parallelToolCalling）；若「把航班所在城市的天气查出来」这种后一步要用前一步结果 → 串行等结果（ToolExecutionMode.sequential）。
3
汇总
各步结果收回来，合成一个回答 / 一组卡片呈现（接回生成式 UI 那套）。

所以「看天气、看航班、改图」这种没关联的，三件事并行发出去、几乎同时回来；而「查 A 城天气，然后订 A 城的酒店」这种前后有依赖的，自动串起来按序执行。并行还是串行，由依赖图决定，不靠模型每次自己琢磨。

注意：能这么编排，前提还是每一步都得是 App Intents 清单里有的标准动作。多任务调度解决的是「怎么排这几件事」，不是「能多做几件清单外的事」——范围依然被前面那张动作清单框死。

把五节连起来看，是同一套思路在反复出现：

模型
端云分工，云只「想」、端才「做」——能力边界与模型大小解耦。
应用
能力很深（深到调滑块），但锁在预设动作域内。
第三方
统一成 Entity 接入，迁就标准换来一致。
规模
平时预建索引、用近似换规模，把大数据在架构层化解。
多任务
拆步骤、按依赖图并行/串行编排，但每步仍限于标准动作。

苹果的强，不在某个模型多聪明，而在这台机器每个环节都「提前把活干好、把范围划清」。

智能可以靠模型堆，但稳、快、不崩、不乱来——是架构给的。
