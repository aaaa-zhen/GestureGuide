Siri 的整体架构

不是一个模型，是一套两百多个框架组成的系统 · 从基座模型，到怎么编排，到开发者怎么接、用户从哪进 · 基于系统私有框架的符号分析

先建立一个总印象

把系统翻开会发现：和 Siri / Apple Intelligence 相关的私有框架有两百多个，由 assistantd 等守护进程串起来。但它不是一团乱麻——是清晰的分层：最底下是模型，往上是「怎么想、怎么调工具」的编排，再往上是上下文和工具，最顶上才是你看到的 Siri、写作工具、视觉智能这些产品形态。

本文先给一张分层全景图，再分别从「一句话怎么流过这套系统」「开发者怎么把 App 接进来」「用户从哪些入口进」三个角度拆开看。

逐层拆开

每一层，到底是什么

上面是骨架，下面把每层翻开，看它由哪些框架组成、关键类怎么运作。

① 基础设施层：一个可查询的「个人知识平台」

IntelligencePlatform 不只是「地基」——它本身是一套个人数据的查询引擎。挖开看：

IntelligencePlatformQuery
一套 SQL 虚拟表引擎（SQLConnection / VirtualTable / ResultSetCursor）——把分散的个人数据当成可 SQL 查询的表。
…DataActions
GlobalKnowledgeQueryService / ActionsQueryService——查「你用过哪些 App、去过哪、活动片段」等可执行的数据动作。
EntitySubgraphService
从大知识图谱里切出「和当前相关」的子图，喂给上层，而不是把整张图丢上去。
assistantd
总守护进程，串起 XPC 通信、特征开关、遥测、隐私边界。

② 模型层：一个基座 + 一堆任务适配器

核心是 AFMInference（Apple Foundation Model 推理），用 actor 模型组织（AFMInferenceActor / AFMInferenceProvider）。关键设计是基座不动、适配器换：

baseModel
一个通用基座大模型，常驻。端侧一套、Private Cloud Compute 一套。
adapterModel（LoRA）
按任务训练的小适配器（adapterModelID / adapterModelMetadata）：改写用一个、总结用一个、规划用一个——换适配器不换基座，省内存、切换快。
AFMDecodeFunctionDescriptor
描述「这次生成怎么解码」——约束解码就挂在这一层（见下）。

③ 上下文层：识屏 + 一个真·知识图谱

给模型决策的「背景」不止屏幕。CoreKnowledge 是一个落盘的个人知识库：

CKKnowledgeStore
知识存储；内容以 CKJSONLDGraph（JSON-LD 图谱）组织——人、地点、App、事件互相连成图。
CKHistoricEvent
历史事件序列——「你昨天做了什么」这类时间线知识。
KnowledgeGraphKit
底层图引擎：节点 / 边 / 谓词 / 过滤，还用 Accelerate 做向量计算（图谱 + 向量混合检索）。
IntelligenceFlowContext
识屏：当前屏幕上的结构化实体（另一篇详解）。

④ 编排层：规划模型 + 工具检索 + 执行会话

这是中枢，由 IntelligenceFlowRuntime（守护进程 intelligenceflowd）驱动：

PlannerAgent
一个专门的「规划模型」（PlannerAgentModel），被训练来拆任务、选工具、生成执行计划。
ToolRetrieval（查库）
工具不是全塞给模型——ToolRetrievalDatabaseConfiguration 表明它从工具数据库里检索相关的几个（ToolRetrievalSearchResult），再给 Planner。
ToolExecutionSession
一次请求的工具执行会话，按依赖图并行 / 串行调（parallelToolCalling）。
ConstrainedDecoding
约束解码——把工具清单变成 token 白名单（allowedTokens / allowedTokensClasses），模型生成时只能吐出清单内的工具名和参数。

⑤ 工具层 / ⑥ 产品层

这两层在后面「开发架构」「产品架构」两个视角里细讲——工具层是 App Intents / AssistantSchema（开发者怎么把能力接进来），产品层是 Campo / 视觉智能 / 写作工具（用户从哪进、结果怎么呈现）。

视角一

一句话，怎么流过这六层

「把刚拍的照片调亮，存进旅行相册」——跟着它走一遍，每一层的角色就清楚了：

1入口接住：产品层（Siri / 打字 / 视觉智能）收到请求，标好「从哪进来的」。EntryPoint · requestSource
2选模型：按设备能力决定端侧还是上云。deviceCapability · pccAsDefault
3装上下文：识屏给「当前是哪张照片」，知识层给「旅行相册是哪个」。IntelligenceFlowContext
4规划：Planner 把它拆成步骤、选出对应的 App Intents 工具、排好顺序。PlannerAgent · GeneratePlan
5约束生成：模型生成「调哪个工具、填什么参数」时被强制只能从清单里选（见下）。ConstrainedDecoding
6端侧执行：计划回到端侧执行器，真正调 Photos 改图、存相册。ExecutorAppIntent
7呈现：结果交回产品层，渲染成卡片 / 朗读。Campo（生成式 UI）

编排层的两个关键设计

① 规划用的是一个专门的「规划模型」（PlannerAgent / PlannerAgentModel）——不是拿通用模型随便答，而是有个被训练来「拆任务、选工具」的角色。多任务时它按依赖图决定并行还是串行（parallelToolCalling / ToolExecutionMode）。

② 约束解码（ConstrainedDecoding）是「不出幻觉工具」的物理保证。模型在生成工具调用时，被语法强制只能产出清单里真实存在的工具名和参数——它想编一个不存在的工具都生成不出来。这就是为什么 Siri 不会「调用一个根本没有的 App 功能」。封闭，不是靠提示词约束，是靠解码层焊死。

看出规律了：云负责「想」、端负责「做」，而「想」本身还被约束解码框在工具清单内。智能可以很强，但能做什么始终是确定、可控的。

视角二 · 技术

开发架构：系统内部怎么运作

抛开产品，看系统自己。一次请求在内部要喂进去四种东西、走一套工具机制——这是「它凭什么答得准」的技术底座。

上下文：当下这一刻的背景

模型决策前，系统先拼出「现在的处境」。它不是只看你说的话，而是把多路上下文一起注入：

屏幕上下文
识屏：当前屏幕的结构化实体（你在看哪张照片、哪条消息）。IntelligenceFlowContext
会话上下文
本轮对话的来龙去脉、上一句指代了什么。IntelligenceFlowConversationRuntime
设备 / 时空
时间、地点、当前前台 App、设备状态。

Personal Context：你是谁

再叠一层「关于你的长期背景」。这是一个落盘的个人知识图谱（CoreKnowledge.CKKnowledgeStore，JSON-LD 图谱），把你的联系人、常去地点、App 使用、历史事件连成图。请求时只切出相关子图注入（EntitySubgraphService），不是把你整个人生塞给模型。

CKKnowledgeStore
持久个人知识库（CKPersistentStoreHandler 落盘）。
CKHistoricEvent
历史事件时间线——「你上周做过什么」。
assertFact
往知识库里断言一条事实并持久化的写入口。

长期记忆 & 自我学习：明天还记得吗？

系统确实有持久记忆（MemoryStore + memoryPersister 落盘）和反馈学习（feedbackLearning.donateInteraction / interactionHistory 带评分权重）。但要分清两种「记住」：

✓ 隐式学习（强）
  • 从你反复的行为里学：常给谁发消息、几点开什么 App
  • 交互被 donateInteraction 记录、按 scoreWeight 加权
  • 转化成「建议 / 排序」，越用越顺手
? 显式偏好（弱 / 不确定）
  • 「我不吃辣」这种随口一句的规则
  • 系统有 assertFact 能存事实的机制
  • 但「随口说 → 自动记成规则 → 明天主动应用」这条链，接口层看不出已贯通——更可能要靠明确的设置 / 重复行为，而非一句话

所以诚实的答案：「今天说不吃辣、明天点外卖自动避开」——苹果有做到它的底层零件（持久事实 + 反馈学习），但是否真的「一句话就记住并主动用」，符号层无法证实。它更擅长从你做了什么学，而不是你说了一句什么。

Tool 调用：怎么从一堆能力里挑对的

工具（App Intents）可能成百上千，不可能全塞给模型。机制是「检索 + 约束生成」：

ToolRetrieval
先从工具数据库里检索出和当前请求相关的几个（ToolRetrievalDatabaseConfiguration / SearchResult），不是全量。
PlannerAgent
专门的规划模型，决定调哪个、按什么顺序。
ConstrainedDecoding
生成工具调用时被 token 白名单（allowedTokens）焊死——只能吐出真实存在的工具和参数，编不出假的。
ToolExecutionSession
按依赖关系并行 / 串行执行，结果回收。

视角三 · 产品

产品架构：能干什么，不能干什么

抛开内部，从用户角度看：这套系统的能力边界到底在哪。

从哪些入口进

多个入口，共用底下同一套编排 + 模型（只是 EntryPoint 不同）：Siri / 打字 Siri（下指令）、识屏（问屏幕上的东西）、视觉智能（举着问「这是什么」）、写作工具（选中文本改写 / 总结）、通知摘要 / 建议（主动推）。

能干什么 vs 不能干什么

✓ 能
  • 调第一方 App 的标准动作：建相册、发邮件、开灯、改图（深到调滑块）
  • 调第三方：只要它接了 App Intents / HomeKit
  • 跨 App串多步：查 A 再据此做 B
  • 读屏、查个人知识、改写 / 总结 / 视觉问答
✕ 不能
  • 做标准动作域之外的事——App 没暴露的功能够不着
  • 调任意外部工具 / 脚本（无 CLI、无任意插件）
  • 编一个不存在的能力——约束解码焊死了
  • 上云也不增加能做的事，只让「想」更聪明

一句话框定边界：能力 = 所有 App 通过标准 schema 暴露出来的动作之和，一个不多、一个不少。智能可以无限涨，但能做什么是这张清单决定的。

多任务并行是怎么样的

一句话里好几件事（「看天气、查航班、把照片调亮存相册」），系统把它当复合请求（compoundRequest）处理：拆成步骤（planStep）→ 看步骤间有没有数据依赖（dependencyGraph）→ 无依赖的并行同时发（parallelToolCalling）、有依赖的串行按序等结果 → 汇总成一个回答。

所以「看天气 + 查航班 + 改图」三件无关的事并行、几乎同时回来；而「查 A 城天气 → 订 A 城酒店」这种前后依赖的自动串起来。并行还是串行由依赖图决定，不靠模型每次自己琢磨——但每一步仍限于标准动作清单。

把三个视角合起来，整套架构的设计意图就一句话：

用分层把「智能」和「能做什么」彻底分开。模型层负责智能，可以靠端云、靠更大的模型不断变强；而「能做什么」被工具层、约束解码、标准 schema 死死框住，稳定、可控、可审计。上限交给模型，下限交给架构。

两百多个框架，最终就为了这一件事：让一句话，安全、一致地变成设备上真正发生的动作。
