弹簧 Spring，以及苹果为什么离不开它

苹果的动画好在哪一层？为什么是弹簧而不是缓动曲线？每个概念配一个能拖的 demo。

1 · 为什么是弹簧，不是曲线 核心

区别不在「好看」，在「能不能被打断」。

下拉一个面板松手，它弹回去——这个「弹回」不是预设的定时动画，而是实时模拟的弹簧。理解苹果动画，从这个区别开始。

"用时长和缓动曲线参数化的动画 API，在底层上与连续、流畅的交互是冲突的。"

Andy Matuschak · 前 Apple UIKit 团队

你在动画软件里画的缓动曲线，本质是 时长 + 曲线形状（像 0.3s ease-in-out）。它是基于时间的：给定 t，查出 value。平时没问题——直到动画中途被打断。

下面两个点都从左滑到右，跑到一半我强制把目标改回左边。看它们各自怎么反应：

缓动曲线（基于时间）点轨道任意时刻打断
弹簧（基于状态）
缓动曲线：打断时重开一段补间，速度被丢弃 弹簧：打断时只改目标，速度被保留
上方是真实滑动的球，下方 canvas 记录它们的位置-时间轨迹。虚线是打断时刻：曲线在此有个肉眼可见的折角，弹簧先减速、再调头。点轨道任意时刻也能手动打断。

曲线版被打断时，位置是连续的，但速度瞬间反向——出现一个折角，看着就「顿」了一下。弹簧版速度始终连续：它先减速、再调头，像真的有惯性。

弹簧适合交互，因为它基于状态，而非基于时间。它随时知道自己的位置和速度；任意时刻改变目标，都能在保留动量的前提下平滑转向。它没有固定「总时长」——何时停下，由物理状态决定。

2 · velocity 继承

承上：spring 顺滑的本质是 新目标来时，旧速度被继承进下一段运动。

连续点击「换目标」，故意在小球还没停时就再点。曲线版每次都从 0 速度重启（一顿一顿），spring 版把当前速度带进去（连贯流动）：

曲线 · 每次从静止重启
spring · 速度尾巴 = 继承的 velocity
曲线：每段从 v=0 重启spring：v 连续继承
这就是为什么对 Siri 说话、它的波形/球可以 实时跟着你的语音强度变 而永远不顿——每次新目标都软着陆在当前运动上。动画软件的关键帧做不到，因为关键帧之间是固定曲线。

3 · 苹果对弹簧做了哪些取舍

它没照搬物理课本。每一处偏离，都是为了设计师好用。

教科书的弹簧（F = −kx − bv 数值积分）很真实，但对做产品的人有几个痛点。苹果在 UIKit / SwiftUI 里改了四个地方，方向都一样：用一点物理纯粹性，换设计上的可控。

取舍一 · 让弹簧「可以设时长」。传统弹簧没有时长——你给刚度阻尼，它自己决定多久停。但设计师的语言是「这个动画 0.5 秒」。苹果的 spring(duration:bounce:) 把它反过来：你说「多久」和「多弹」，系统反推刚度阻尼。于是你既能像曲线一样指定时长，又保留了弹簧的可打断。四个改动里这是最反直觉的一个。

注意：调的是「时长」和「弹性」——而不是抽象的刚度/阻尼。bounce=0 时无过冲（接近 ease）；越大越弹。虚线 = duration 标记，曲线在它附近基本到位。

取舍二 · 为「可预测」牺牲纯物理。真实弹簧理论上 永远不会真正停下——振幅指数衰减，无限趋近但不到零。产品里不能这样：动画得有个明确的「结束」，否则永远在重绘、耗电。苹果用一个 静止阈值 解决：当速度和距离都小到一帧内看不出变化，直接吸附到终点、停止。安卓的同款机制叫 minimumVisibleChange。这是工程对物理的妥协，但用户只会觉得「干净地停住了」。（第 4 节会把数值 spring 这个「永不到零」的细节展开。）

取舍三 · 速度由系统自动接管。你拖一个视图甩出去，松手那一刻，手指的速度被自动注入弹簧——你不用写任何代码去测速、传递。UIKit / SwiftUI 在手势识别器里内建了这条链路。iOS 所有「滑动惯性」都来自这里——第 2 节的「velocity 继承」，系统替你做了。

取舍四 · 默认值本身就是设计语言。SwiftUI 给了几个预设弹簧：.smooth、.snappy、.bouncy。它们不是随手填的数，而是 经过调校、保证全系统手感统一 的一套规范。大多数苹果工程师从不手写刚度阻尼——直接用预设，于是整个系统的动画手感天然一致。

总结：苹果把「物理上正确的弹簧」改成了「设计上好用的弹簧」——可设时长、保证停止、自动接管速度、默认即规范。

4 · 解析 spring vs 数值 spring：分界线不是解法，是状态

苹果 shader 里的 overshoot 公式，就是阻尼弹簧方程的 精确解析解——不是近似、不是手调曲线，反而比数值积分还准。真正的分界线也不在「解析 vs 数值」，而在 带不带状态。用无状态闭式只为一件事：它是 t 的纯函数，能塞进 shader，还能干净、可预测地停下来。

同一个微分方程 mẍ + bẋ + kx = 0，两种用法，静态结果几乎重合（下面叠加可见）。区别全在「怎么停」和「能不能被打断」——而这两条都由 状态 决定，不由解法决定：

带状态 · 逐帧推进（chenglou / 安卓 / SwiftUI 交互式） 无状态 · t 的纯函数（苹果 shader 公式）
怎么算 每帧拿当前 (x, v) 推进一步 dt。内部可以是欧拉积分（chenglou 的 v += a·dt），也可以是闭式推进（安卓 SpringForce 拿当前 x、v 当初值，解析算出 dt 后的状态）
数值/解析不是这一列的分界		 直接套 1−e^(−l·t)·cos(w·t)，整条轨迹是 t 的显式函数
怎么停 渐近，永不到零 → 逐帧判吸附阈值
安卓 minimumVisibleChange / chenglou 的 |v|<0.01 && |dest−pos|<0.01		 阈值只用一次：预解出停止时刻 T ≈ ln(1/ε)/l 当时长，到 T 钳到终值
CASpringAnimation 的 settlingDuration 即此。逐帧零判断，但 ε 还在
能否被打断 能，(x, v) 是状态，随时换目标、velocity 继承 这个两参数公式不能（初条件写死、没有 v₀）。但通用闭式解可以：x(t) = e^(−l·t)·[x₀·cos(w·t) + ((v₀+l·x₀)/w)·sin(w·t)]，打断时取当前 (x, v) 重新锚定
CASpringAnimation / SwiftUI Spring 正是这么做的
数值积分解析闭式解 1−e^(−λt)·cos
从 Siri shader 逆向出的两个函数，就是这个方程两种阻尼情形的精确解：
settleWL(t,w,l) = 1 − e^(−l·t)·cos(w·t) ← 欠阻尼，cos 项 = overshoot 回弹。一个细节：它隐含初速度 v(0) = l（求导可得），不是静止出发；静止出发的精确解多一项 (l/w)·sin(w·t)，l 不大时肉眼无差
settleCrit(t,l) = 1 − e^(−l·t)·(1+l·t) ← 临界阻尼、零初速的精确解，无过冲单调到位
两个都是货真价实的解析解。苹果在 shader 里选它们，是因为 shader 必须是 (time, uniforms) 的纯函数、存不了状态——「能干净地停」是这个约束下顺手的收益。
「看似停了其实还在跑」是带状态逐帧推进的固有问题，不是解析解的： 逐帧 spring 的 e^(−t) 渐近趋零、理论上永不到零，不掐断就会以 0.0001px 的振幅一直动下去，每帧白白计算和重绘。 解法是吸附阈值——安卓的 setMinimumVisibleChange()（按像素/角度给阈值），chenglou 写作 |v|<0.01 && |dest−pos|<0.01 → 直接归位。两个条件缺一不可： 只判位置会在穿过目标的瞬间（pos≈dest 但 v 很大）误停；只判速度会在过冲顶点（v≈0 但离目标最远）误停。 而苹果的纯函数解不是不要阈值，是把阈值用在另一头：ε 只花一次，预解出停止时刻，到点钳位——逐帧再无判断。
苹果 UI 层的闭式 spring 怎么做到可打断：CASpringAnimation / SwiftUI Spring 用的是带初条件的通用解 x(t) = e^(−λt)·[x₀·cos(ωt) + ((v₀+λx₀)/ω)·sin(ωt)]——x₀ 是离目标的距离，v₀ 是当前速度。打断时三步：
① 取当前状态：位置直接读（CoreAnimation 读 presentationLayer）；速度也不用积分器——闭式解可以解析求导，x′(t) 代入当前时刻就是精确的瞬时速度
② 重新锚定：以新目标为原点，把刚取出的 (x, v) 当新一段的 (x₀, v₀)，时间从 0 重起
③ 新一段的初速度 = 上一段的末速度，位置和速度都连续——没有折角
本质是「分段无状态」：段内是 t 的纯函数，状态只在打断的那一刻被捕获、传递一次。

一句话收尾：可打断 ⇔ 携带 (x, v) 状态。解析还是数值只是「怎么推进」的实现细节——安卓用闭式逐帧推进、SwiftUI 的闭式弹簧照样可打断，都是证据。苹果 shader 选无状态版，是 GPU 纯函数约束下的工程取舍，不是解析解的数学限制。

5 · 什么时候用 spring，什么时候不用

讲了四节 spring，但不是所有运动都适合 spring。

6 · 旋转：永远在跑的运动，用 linear

第一层：旋转——没有起止、没人打断的背景运动。

匀速就是对的。加 ease 反而会「一顿一顿」：

永远在跑的运动 → linear。

7 · 缩放：预定循环的运动，用 ease

第二层：缩放——大小的呼吸循环。预定好、永远没人打断，这种就该用 ease。

节奏固定，「不可打断」这个缺点就无所谓了。6 颗球相位错开，才像活物：

预定的循环 → ease。

8 · 移动：会被打断的运动，用 spring + velocity

第三层：移动（穿心）。唯一会被打断的运动——这才轮到 spring。每球一个独立 spring（反汇编符号 FluidDotsParamsV12SpringConfigV）。

· 全员穿心——改目标，spring 把球带过去
· 移动途中点一下 dots——打断：velocity 被继承，带着惯性调头
· 聚合→爆开——还是这组 spring，只是改目标值
· 只给 velocity——不设目标，只给初速度：够快就穿到对面，不够就弹回来。iOS 翻页就是这个逻辑

会被打断的运动 → spring。穿心到一半点一下试试。
